# Inventario y gobierno de sistemas de IA — TrackFlow

**Fecha de revisión:** 2026-10-27. **Alcance:** código de este fork y documentación disponible; no es una certificación de producción ni un pentest.

### Barrera de autorización añadida (2026-10-27)

Las rutas de conocimiento/RAG y chat WebSocket ahora exigen rol `ADMIN` o `MANAGER`; las rutas de lectura y cambio de estado de incidencias reservan acceso a esos roles y a la identidad explícita `SERVICE`, mientras que crear incidencias y analizar CSV quedan solo para operadores (en MCP, los scopes OAuth por herramienta siguen siendo necesarios). Los roles `USER` reciben 403 antes de invocar el agente o consultar incidencias. Esto reduce la exposición entre cuentas de cliente y la superficie de datos globales, pero **no es aislamiento multi-tenant**: el modelo aún no tiene pertenencia usuario–tenant ni `tenant_id` en incidencias/documentos, y un operador o SERVICE autorizado ve datos globales. No se debe usar para prometer separación entre marcas. La cuenta técnica MCP existente, creada como usuario normal, debe ser elevada deliberadamente por un administrador a `service` y sus scopes MCP revisados; no hay elevación automática. Para habilitar el servicio con rol USER se deniega la petición en fail-closed.

## Gobierno de terceros

TrackFlow mantiene responsabilidad sobre base legal, selección y minimización de datos, configuración, control de acceso, validación de las salidas y autorización de acciones, aunque el LLM, vector store, OAuth, cloud o courier sea externo. Seguridad/Compras/Legal deben validar contratos, ubicación/transferencias, retención, subprocesadores, notificación de incidentes y mecanismos de borrado. Ninguna clave de courier debe estar disponible desde rutas de chat B2C.

## Confirmación humana de acciones irreversibles del briefing

Se consideran acciones de alto impacto y requieren confirmación humana explícita antes de ejecución: aprobar una devolución por encima del umbral definido por Operaciones; confirmar despacho de envío de alto valor; cambiar carrier de envío en tránsito; compartir volumen/incidentes de una marca con otra. **Estado del fork revisado:** los flujos de aprobación de devoluciones, despacho de alto valor y cambio de carrier no quedaron demostrados; el compartir entre tenants también requiere verificación. El requisito se registra como brecha crítica de diseño y no se afirma como protección ya desplegada. El flujo MCP de cambio de inventario se describe como deny-only, no como aprobación humana implementada.
