## Chat WebSocket en tiempo real — Parte 2 (2026-10-22, rama feature/websocket-chat)
- Implementado `WebSocket /chat/ws/{session_id}?token=<JWT>` en `services/api/src/routes/chat_router.py`, reutilizando JWT y el agente existente `first_line_cx` vía `invoke_agent`; `session_id` se conserva también como `run_id`/LangGraph `thread_id`.
- Generación de chat en modo stream con parser incremental del campo JSON `answer` (sin emitir `proposal`), mensajes/eventos estructurados y pub/sub en memoria por sesión. Sesiones e historial, estado del mensaje y watermark `sequence` se guardan en TinyDB. La UI `/knowledge` consume chunks, reintenta conexión y rehidrata el parcial streaming mediante snapshot + `replace`.
- Interrupción cooperativa: se señala cancelación, se solicita cerrar el stream activo y se espera a que la generación anterior se detenga antes de marcar el parcial `interrupted` e iniciar la redirección. No usa `LangGraph interrupt()`/HITL. La cancelación confirmada por tests es con generador controlable; falta validar si el proveedor configurado termina inmediatamente el cómputo remoto tras `close()`.
- Respuestas de diseño: WebSocket por bidireccionalidad; un productor/pub-sub por sesión para consumidores múltiples; JWT y propiedad validados antes del snapshot; TinyDB para rehidratación local y checkpointer PostgreSQL existente para estado LangGraph; pub/sub en memoria solo soporta un proceso (Redis/backplane necesario para réplicas); `client_id=user_id` provisional porque no existe entidad Client explícita.

## Notificaciones RFP en tiempo real (2026-10-21, rama feature/sse-notifications)
- Implementado endpoint autenticado `GET /rfp/events` con JWT del backoffice, framing SSE nombrado `rfp_ticket_created`, JSON plano, keep-alive y headers anti-buffering/no-cache. El evento se genera solo tras clasificación positiva con status wire `analyzing`; no se invocan modelos/agentes adicionales.
- El evento se publica desde el callback del clasificador existente. Los metadatos opcionales no disponibles son `null`; `issuing_organization` y `rfp_reference` no se fuerzan a `client_name`/`rfp_id`. La persistencia durable sigue siendo SQLModel sobre PostgreSQL/Supabase; estados internos existentes en español se mapean al wire contract sin cambiar el modelo.
- Fan-out multiinstancia por Redis Pub/Sub sobre `REDIS_URL` ya existente y canal `trackflow:rfp:events:v1`; suscriptor iniciado y detenido con lifespan FastAPI, reintento de conexión y colas locales acotadas. Redis es transporte efímero, no una garantía de entrega durable ni fuente de verdad. Si Redis falla, subsiste el fan-out local y el cliente se reconecta/recupera desde Supabase.
- Backoffice consume con `fetch` + `ReadableStream` (Bearer JWT), backoff exponencial 1–30 s y deduplicación por ticket. En cada conexión SSE (también la inicial), abre primero el stream, consulta después el listado durable y empieza a consumir frames al terminar el snapshot; esto cubre eventos durante la carga y pérdidas durante desconexión.
- Respuestas de diseño: (1) SSE vs WebSockets: SSE porque es servidor→dashboard unidireccional; WebSockets solo si se necesita interacción bidireccional en el mismo canal. (2) Escala: cada navegador conserva una conexión SSE y cada réplica una suscripción Redis; 50 clientes equivalen a 50 streams distribuidos entre réplicas y fan-out local. Redis Pub/Sub resuelve propagación multiinstancia, pero no persiste mensajes; Supabase refetch recupera tickets, no entrega individual exactamente una vez. Outbox + Redis Streams sería la evolución si se exige entrega durable.
- Documentación operacional y checklist en `docs/rfp-realtime-notifications.md`; prueba manual: abrir dashboard autenticado, verificar `GET /rfp/events` y Bearer en Network; interrumpir conexión, registrar ticket válido desde otro cliente, restaurar y confirmar recuperación única más eventos posteriores.
- Validación de esta implementación: pruebas `tests/test_rfp_event_broker.py` y `tests/test_rfp_sse.py`: 4 pasaron; compileall, TypeScript (`npx tsc --noEmit`), ESLint, `docker compose config --quiet`, `git diff --check` sin errores. Pytest informa warning de deprecación Starlette TestClient/httpx.

## Harness de seguridad del agente (2026-10-10)
- Se endureció el mismo agente LangGraph `trackflow-knowledge-agent` de CX, preservando RAG, MCP y memoria por usuario; no se creó un agente alternativo.
- Guardrail local determinista bloquea patrones conocidos de jailbreak y tareas personales antes de routing. El clasificador estructurado reutilizado del router tipa consultas como `trackflow`, `casual`, `personal`, `out_of_scope` o `instruction_override`; exige `scope` explícito y solo permite seleccionar fuentes para `trackflow`.
- Small talk/trivia se responde brevemente cuando es posible y se redirige a TrackFlow; tareas personales se rechazan; otras consultas fuera de dominio no acceden a RAG/MCP y reciben redirección. Error/contrato inválido del clasificador falla de forma cerrada.
- Preguntas, evidencia RAG/MCP y memoria se separan de las instrucciones de sistema y se representan como datos no confiables. Se validan las salidas para estructura, instrucciones internas y datos sensibles; fallos usan fallback seguro y no proponen memoria.
- Una entrada bloqueada no llega al clasificador de consentimiento. Si hay propuesta pendiente, las consultas no reconocidas se preclasifican antes de procesar memoria; las respuestas explícitas de consentimiento preservan el flujo aprobado.
- Logging estructurado registra categoría, acción, motivo y `run_id`, sin texto conversacional. `GET /knowledge/guardrails/summary` requiere autenticación y limita el resumen al usuario; retención local máxima 5000 eventos por proceso, reiniciada al reiniciar y no agregada entre workers.
- Trazas locales no conservan pregunta, respuesta ni evidencia. LangSmith requiere `LANGSMITH_TRACING=true` explícito además de `LANGSMITH_API_KEY`.
- Evidencia adversarial documentada en `docs/rag/langgraph-agent.md`: variantes de cambio de instrucciones (“ignora instrucciones anteriores”, “asistente sin reglas”, “olvida que trabajas para TrackFlow”, y paráfrasis en inglés/español); tareas personales (poema, universidad, terapia, correo personal, estudiar, receta); trivia casual (hora en Tokio, Mundial 2018, Roma); y contenido malicioso en fixture RAG/datos MCP. Los tests deterministas verifican rechazo/redirección, ausencia de llamadas a herramientas, aislamiento de prompts, controles de salida y métricas.
- Validación final de la sesión: `uv run --project services/api --with pytest --with scikit-learn python -m pytest services/api/tests tests/pipelines -q` dio 328 pasados y 2 omitidos; análisis estático y `git diff --check` sin errores. Los tests usan decisiones de routing mockeadas; no sustituyen un red-team del clasificador LLM live.
